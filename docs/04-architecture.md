# 4. Архитектура

## Главная идея

Страница собрана из **независимых модулей**. Каждый модуль:

- живёт в своей папке `src/modules/<имя>/`;
- «включается» атрибутом `data-module="<имя>"` в HTML;
- получает свой элемент и общий контекст: `init(element, ctx)`;
- возвращает `{ destroy() }` — функцию полной уборки;
- **не знает о других модулях**; если нужно общение — через шину событий.

Благодаря этому любой модуль можно удалить из страницы, перенести в другой проект или
переписать, не трогая остальные.

## Слои проекта

```
┌──────────────────────────────────────────────────────────────────────┐
│ index.html — вёрстка, тексты, data-атрибуты                           │
├──────────────────────────────────────────────────────────────────────┤
│ src/main.js — точка входа: стили, шрифты, СПИСОК модулей              │
│ src/app.js  — приложение: общий слой, страницы, переходы, роутер       │
├───────────────┬─────────────────────────────────┬────────────────────┤
│ src/content/  │ src/modules/<имя>/              │ src/styles/        │
│ данные и      │ эффекты                          │ CSS                │
│ шаблоны       │   index.js    — подключение к DOM│                    │
│               │   *.js        — чистая логика    │                    │
│               │   *.scene.js  — WebGL (three.js) │                    │
│               │   *.glsl.js   — шейдеры          │                    │
│               │   README.md   — описание         │                    │
├───────────────┴─────────────────────────────────┴────────────────────┤
│ src/core/ — ядро: gsap, registry, lifecycle, bus, env, webgl, media,  │
│ math, rng, fps. Ничего не знает о секциях страницы.                    │
└──────────────────────────────────────────────────────────────────────┘
```

**Правило зависимостей:** стрелки идут только вниз. `core` ни от кого не зависит, `modules`
зависят от `core` (и иногда от `content`), но **не друг от друга**. Одно исключение —
`gallery/lightbox.js` берёт `escapeHtml` из `content/render.js`.

## Внутри модуля: три вида файлов

Почти каждый модуль разделён одинаково — и это самый полезный приём для переноса кода:

| Файл | Что внутри | Зависит от | Пример |
| --- | --- | --- | --- |
| **Чистая логика** (`flight.js`, `engine.js`, `math.js`, `state.js`…) | Формулы и состояние: «где должен быть слайд», «смахнуть или вернуть», «куда летит ракета». Без DOM, без GSAP, без three. | только `core/math.js` | `sliders/infinite/engine.js` |
| **Подключение** (`index.js`) | Ищет элементы, вешает события, связывает жесты с логикой, логику — с рендером. | GSAP, DOM, логика | `sliders/infinite/index.js` |
| **Рендер** (`*.scene.js`, `dom-renderer.js`) | Рисует то, что посчитала логика: DOM-трансформами или в WebGL. | three.js или DOM | `sliders/infinite/infinite.scene.js` |

Почему так:

1. **Чистую логику легко тестировать** — это обычные функции «числа на входе → числа на
   выходе», им не нужен браузер (все такие файлы покрыты тестами).
2. **Чистая логика переносится на любой стек без изменений** — React, Vue, Svelte, даже
   React Native или игровой движок: формулы пружины или траектории от фреймворка не зависят.
3. **Рендер можно менять**, не трогая логику: бесконечная лента (№3) и барабан (№4)
   используют **один и тот же** движок `engine.js` с двумя разными рендерами.

## Контекст `ctx`

Объект, который получает каждый модуль (создаётся в `main.js`):

| Поле | Что это | Зачем |
| --- | --- | --- |
| `gsap` | GSAP с плагинами | на случай, если модулю удобнее взять его из контекста |
| `bus` | шина событий (`core/bus.js`) | общение модулей без прямых ссылок |
| `quality` | `{ tier, dpr, stars, particles }` | одна «ручка» качества для всех тяжёлых эффектов |
| `reduced` | `true`, если пользователь просит меньше движения | выключить автоанимации |
| `smoother` | экземпляр ScrollSmoother или `null` | прокрутка к якорю, пауза скролла |
| `getScroll()` | текущая прокрутка в px | работает и с ScrollSmoother, и без него |

Модули могут **добавлять** в контекст своё: ракета кладёт `ctx.rocket` (сцена) и
`ctx.rocketSleeping` (для отладочного оверлея).

## Запуск модулей: `registry`

`src/core/registry.js` — 50 строк, которые стоит прочитать целиком. Коротко:

```js
const registry = { ring: ring.init, gallery: gallery.init, /* ... */ } // в main.js
const app = await mountModules(registry, ctx)
// app.mounted — какие запустились, app.failed — какие упали, app.destroy() — убрать все
```

- Модули запускаются **параллельно**; асинхронные (те, что грузят three.js) не задерживают
  остальные.
- Ошибка в одном модуле пишется в консоль, но **не ломает страницу**.
- Порядок уборки — обратный порядку запуска.

## Многостраничность: общий слой и страница

Сайт — несколько обычных HTML-файлов (`index.html`, `missions.html`, `destinations.html`),
но переходы между ними — без перезагрузки:

```
ОБЩИЙ СЛОЙ (живёт всё время)              СТРАНИЦА (пересоздаётся при переходе)
├─ небо .sky                               ├─ <div data-page-fixed> — фиксированные слои
├─ курсор, шапка (data-module)             │   страницы (canvas ракеты на главной)
├─ ScrollSmoother (#smooth-wrapper)        └─ <main data-page="…"> — всё содержимое
├─ занавес page-transition
└─ роутер core/router.js
```

`src/app.js`, функция `navigate(url)`:

1. сразу начинает скачивать HTML новой страницы (`fetchPage`);
2. занавес закрывает экран (`transition.play`), а под ним:
   - `unmountPage()` — `destroy()` всех модулей страницы и параллакса ScrollSmoother;
   - `swapPage(doc)` — подменить `<main data-page>` и `[data-page-fixed]` на новые, сменить
     `<title>`;
   - `history.pushState` — новый адрес в браузере;
   - прокрутка в начало (или к `#якорю`);
   - `mountPage()` — шаблоны (`renderSlots`), модули страницы, параллакс
     (`smoother.effects`), небо (`data-sky`), `ScrollTrigger.refresh()`, событие `page:change`;
3. занавес открывает новую страницу.

Если что-то пошло не так (нет сети), страница открывается обычной загрузкой. Без JavaScript
ссылки работают как обычные.

**Правило для общих элементов:** они повторены в каждом HTML-файле. Меняете шапку — меняйте
во всех файлах. Обработчики общих модулей вешаются на `document` (делегирование), поэтому
работают и на элементах новых страниц.

## Данные отдельно от вёрстки: `content/`

- `photos.js` — список фото: файл, размеры, название, подпись, автор.
- `videos.js` — ролики для видеопанелей.
- `render.js` — **шаблоны**: функции «данные → HTML-строка» и `renderSlots()`, который
  заполняет в HTML пустые контейнеры `<div data-render="имя" data-photos="p01,p05">`.

Почему не написать все карточки прямо в HTML? Восемь одинаковых карточек кольца, шесть
стопки, тридцать в галерее — при правке пришлось бы менять десятки мест. Шаблон описывает
карточку один раз. В React/Vue эту роль играют компоненты — шаблоны `render.js` почти
дословно переписываются в JSX (см. [06-porting.md](06-porting.md)).

## Жизненный цикл модуля на примере

```
init(el, ctx)
 ├─ найти элементы внутри el (querySelector)
 ├─ если чего-то не хватает → return { destroy() {} }   // «пустой» экземпляр, не падаем
 ├─ const d = createDisposer()                           // сюда складываем уборку
 ├─ создать логику (движок, состояние)
 ├─ подписаться на события:      d.listen(el, 'click', …)
 ├─ подписаться на кадры:        gsap.ticker.add(tick); d.add(() => gsap.ticker.remove(tick))
 ├─ следить за видимостью:       d.add(onViewport(el, { enter, leave }))
 ├─ создать анимации в gsap.context: d.add(() => context.revert())
 └─ return { destroy: () => d.dispose(), ...полезные методы }
```

## Стили

| Файл | Что внутри |
| --- | --- |
| `base.css` | Переменные (цвета, шрифты, рамки, фон), сброс, кнопки, шапка, рамки фото, отладка. |
| `sections.css` | Первый экран, манифест, история, орбита, обёртка слайдеров, подвал, маркеры траектории. |

Все цвета, шрифты и «рамки» — CSS-переменные в начале `base.css` (`--accent`, `--cyan`,
`--frame-glow-cyan`, `--space-bg`…). Поменять оформление всего сайта — значит поменять
эти переменные (см. [07-customization.md](07-customization.md)).
