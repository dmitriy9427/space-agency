# 2. Базовые понятия с нуля

Этот документ объясняет всё, на чём построены эффекты проекта. Читать можно с любого места,
но разделы идут от простого к сложному. После каждого раздела указано, где в коде это
используется.

---

## 2.1. Кадр и цикл анимации

**Анимация — это быстрая смена картинок.** Монитор обновляет изображение 60 раз в секунду
(или 120 на «быстрых» экранах). Каждое обновление называется **кадром**. Чтобы что-то
плавно двигалось, мы должны перед каждым кадром немного менять положение этого «чего-то».

В браузере для этого есть `requestAnimationFrame` (сокращённо **rAF**): «браузер, вызови
мою функцию прямо перед следующим кадром».

```js
function tick(time) {
  box.style.transform = `translateX(${time * 0.1}px)` // сдвигаем по времени
  requestAnimationFrame(tick)                           // и просим следующий кадр
}
requestAnimationFrame(tick)
```

**Почему не `setInterval(fn, 16)`?** Интервал не знает о мониторе: он может сработать
между кадрами (работа впустую) или пропустить кадр (рывок). rAF всегда синхронен с экраном
и автоматически останавливается, когда вкладка скрыта, — экономит батарею.

### Тикер GSAP

GSAP уже крутит свой rAF-цикл — **тикер** (`gsap.ticker`). Вместо своего rAF мы
подписываемся на него:

```js
const tick = (time, deltaMs) => { /* time — секунды с начала, deltaMs — мс с прошлого кадра */ }
gsap.ticker.add(tick)    // подписаться
gsap.ticker.remove(tick) // ОБЯЗАТЕЛЬНО отписаться, когда эффект больше не нужен
```

Плюс тикера: все анимации страницы (твины GSAP, ScrollTrigger, наши WebGL-сцены) обновляются
**в одном цикле, в одном порядке**, без лишних rAF.

**В проекте:** все WebGL-сцены (`rocket`, `liquid`, `sliders/infinite`, `sliders/shader`),
галерея, курсор — подписаны на `gsap.ticker`. Обёртка для «цикла, который можно ставить на
паузу» — `createRenderLoop` в `src/core/webgl.js`.

## 2.2. Независимость от частоты кадров (FPS)

Главная ловушка новичка. Код вида

```js
x += 5 // каждый кадр сдвигаемся на 5 px
```

на экране 60 Гц даст 300 px/с, а на 120 Гц — 600 px/с. Анимация на разных устройствах будет
разной. Решение — учитывать **время между кадрами** `dt` (в секундах):

```js
x += 300 * dt // 300 px в секунду при любой частоте
```

### Плавное «догоняние»: `damp`

Очень частый приём: значение не прыгает к цели, а «догоняет» её с замедлением. Наивно:

```js
current += (target - current) * 0.1 // каждый кадр проходим 10% оставшегося пути
```

Это снова зависит от FPS. Правильная формула — **экспоненциальное затухание**:

```js
current += (target - current) * (1 - Math.exp(-lambda * dt))
```

Она даёт одинаковый результат при любом разбиении времени на кадры: два шага по 0.05 с
дают ровно то же, что один шаг 0.1 с. Это функция `damp(current, target, lambda, dt)` в
`src/core/math.js` (и тест, который это проверяет, — в `math.test.js`). `lambda` —
«жёсткость»: чем больше, тем быстрее догоняет.

### Фиксированный шаг

Иногда физику проще считать шагами одинаковой длины (например, ровно 1/60 с). Тогда
накапливаем прошедшее время и делаем столько шагов, сколько «влезло»:

```js
accumulator += dt
while (accumulator >= STEP) { stepPhysics(); accumulator -= STEP }
```

**В проекте:** хвост курсора (`src/modules/cursor/rope.js`) — фиксированный шаг 1/60;
ракета, галерея, лента — `damp`; частицы выхлопа — `spawnBudget` в
`src/modules/rocket/particles.js` (сколько частиц родить за кадр, чтобы в секунду было
одинаково).

## 2.3. Что двигать: `transform`, а не `top/left`

Браузер рисует страницу в несколько этапов: **Layout** (вычислить размеры и позиции всех
элементов) → **Paint** (нарисовать пиксели) → **Composite** (сложить слои на видеокарте).

- Изменение `top`, `left`, `width`, `margin` запускает **Layout** — пересчёт всей страницы.
  Это дорого.
- Изменение `transform` (сдвиг, поворот, масштаб) и `opacity` обычно обрабатывает только
  **Composite** на видеокарте. Это почти бесплатно.

Поэтому все движения в проекте — через `transform: translate3d(...)`, `scale(...)`,
`rotate(...)`. GSAP по умолчанию тоже анимирует `x`, `y`, `rotation`, `scale` через
`transform`.

`will-change: transform` в CSS заранее подсказывает браузеру вынести элемент на отдельный
слой. Использовать точечно: каждый слой занимает видеопамять.

**Исключение в проекте:** видеопанели меняют `flex-grow` (это Layout), потому что ширина
должна реально меняться и сдвигать соседей. Панелей всего пять, и все они меняются одним
твином — это дёшево.

## 2.4. Твин, таймлайн, ease

- **Твин** (tween, от in-betweening) — анимация одного или нескольких свойств от одного
  значения к другому за время:
  ```js
  gsap.to('.box', { x: 200, duration: 1 })       // от текущего к 200
  gsap.from('.box', { opacity: 0 })              // от 0 к текущему
  gsap.fromTo('.box', { x: 0 }, { x: 200 })      // явно оба конца
  gsap.set('.box', { x: 0 })                     // мгновенно, без анимации
  ```
- **Таймлайн** — контейнер, в котором твины идут по расписанию:
  ```js
  const tl = gsap.timeline()
  tl.to(a, { x: 100 })          // сначала a
    .to(b, { y: 50 }, '<')      // '<' — одновременно с предыдущим
    .to(c, { opacity: 0 }, 0.5) // в момент 0.5 с от начала таймлайна
  ```
- **Ease** (кривая сглаживания) — как скорость меняется во времени. `none` — равномерно,
  `power2.out` — быстро в начале и мягко в конце, `elastic.out` — с пружинистым «дрожанием»,
  `expo.out` — резкий старт. Посмотреть все: [gsap.com/docs/v3/Eases](https://gsap.com/docs/v3/Eases).
- **stagger** — сдвиг старта для группы элементов: буквы заголовка появляются не разом, а
  «волной» (`stagger: 0.035` — каждая следующая на 35 мс позже).

**В проекте:** заголовок первого экрана (`modules/hero/index.js`) — таймлайн из трёх твинов;
история (`modules/story`) — таймлайн, который ведёт скролл.

### `gsap.context()` — уборка за анимациями

Все твины, ScrollTrigger-ы и SplitText, созданные внутри `gsap.context(() => { ... })`,
запоминаются, и `context.revert()` убирает их разом и возвращает DOM в исходное состояние.
Это основной способ «чисто выключить» эффект (важно для React/Vue, см. [06-porting.md](06-porting.md)).

## 2.5. Анимации от скролла: ScrollTrigger

ScrollTrigger связывает анимацию с положением прокрутки.

```js
gsap.to('.title', {
  yPercent: -35,
  scrollTrigger: {
    trigger: '.hero',      // за каким элементом следим
    start: 'top top',      // когда ВЕРХ элемента дойдёт до ВЕРХА экрана — начало
    end: 'bottom top',     // когда НИЗ элемента дойдёт до ВЕРХА экрана — конец
    scrub: true,           // анимация «привязана» к скроллу (крутишь назад — она назад)
  },
})
```

- **`start` / `end`** записываются как «точка элемента + точка экрана»: `'top 65%'` =
  «верх элемента на 65% высоты экрана». Можно добавить `markers: true`, и ScrollTrigger
  нарисует эти линии — лучший способ отладки.
- **`scrub: true`** — прогресс анимации = прогресс скролла. `scrub: 0.8` — то же, но анимация
  догоняет скролл за 0.8 с (мягче).
- **`pin`** — «закрепить» элемент: секция стоит на месте, пока скролл проигрывает таймлайн.
  ScrollTrigger сам добавляет нужный отступ (pin-spacer), чтобы страница не «прыгала».
- **`onUpdate(self)`** — вызывается при каждом изменении: `self.progress` (0…1),
  `self.direction` (1 вниз / −1 вверх), `self.getVelocity()` (скорость скролла, px/с).
- **`once: true`** — сработать один раз (например, запустить счётчик при появлении).
- **`ScrollTrigger.refresh()`** — пересчитать все позиции. Нужен, когда изменилась высота
  страницы: подгрузились шрифты или картинки, создали новый пин.

**В проекте:** история (pin на 4 экрана), орбита (pin + scrub), галерея (pin + скролл двигает
сетку), путевые точки ракеты (ScrollTrigger используется только чтобы *измерить* позиции
секций — см. `modules/rocket/index.js`).

## 2.6. Плавный скролл: ScrollSmoother

Обычный скролл колесом идёт рывками по 100 px. ScrollSmoother делает его плавным: настоящая
прокрутка страницы происходит как обычно, но видимое содержимое догоняет её с инерцией.

Как это устроено: всё содержимое страницы кладётся в две обёртки:

```html
<div id="smooth-wrapper">        <!-- фиксирован на весь экран, обрезает лишнее -->
  <div id="smooth-content">      <!-- сдвигается transform-ом вслед за скроллом -->
    ...вся страница...
  </div>
</div>
```

**Важное следствие:** `position: fixed` внутри `#smooth-content` перестаёт работать
(элемент внутри родителя с `transform` фиксируется относительно родителя, а не экрана).
Поэтому фон, canvas ракеты, курсор и шапка лежат **снаружи** обёрток (см. `index.html`).

Бонус: атрибуты `data-speed="0.85"` (параллакс — элемент едет медленнее) и `data-lag="0.2"`
(элемент догоняет с задержкой) работают без кода.

**Почему не на телефоне:** на тач-экранах родная инерция прокрутки и так плавная, а подмена
скролла может ощущаться «ватной». В `main.js` плавный скролл включается только для мыши.

## 2.7. Пружины и инерция

### Инерция («бросок»)

Когда отпускаешь перетаскиваемый объект, он продолжает движение и замедляется. Нужна
скорость в момент отпускания: её считают по последним точкам движения
(`createVelocityTracker` в `modules/sliders/stack/state.js` — скорость за последние 100 мс).

InertiaPlugin делает это сам: `Draggable.create(el, { inertia: true })`, а `snap` докручивает
до ближайшего «правильного» положения (так работает 3D-кольцо).

### Пружина

Пружина тянет значение к цели с силой, пропорциональной расстоянию, а трение гасит скорость:

```js
acceleration = -stiffness * (x - target) - damping * velocity
velocity += acceleration * dt
x += velocity * dt
```

- мало трения → значение проскакивает цель и качается (отскок);
- много трения → подходит плавно без перелёта («критическое демпфирование»).

В `modules/sliders/infinite/engine.js` это `springStep`, а `springFrom(duration, bounce)`
переводит «человеческие» параметры (время доводки и пружинистость 0…1) в физические.

### Почему хвост курсора сначала «взрывался»

Цепочка из многих пружин, где каждая тянется за предыдущей, может **усиливать** колебания:
каждое звено чуть раскачивает следующее, и на 26-м звене амплитуда огромная. Решение —
сделать звено **передемпфированным** (оно никогда не проскакивает цель). Подробный разбор —
в комментарии в начале `modules/cursor/rope.js`.

## 2.8. Бесконечность: заворот по модулю

Бесконечная лента и бесконечная сетка не содержат бесконечного числа элементов. Их 8–30, и
когда элемент уходит за один край, он **переставляется** на другой.

Математически: позиция элемента берётся «по модулю» длины ленты.

```js
const total = slideWidth * count
x = wrap(index * slideWidth + scroll, -total / 2, total / 2)
```

`wrap(v, min, max)` (`core/math.js`) возвращает `v`, «свёрнутое» в полуинтервал
`[min, max)`: число 12 в диапазоне [0, 10) станет 2, а −3 станет 7.

Обычный оператор `%` в JavaScript для отрицательных чисел даёт отрицательный остаток
(`-3 % 10 === -3`), поэтому в проекте используется своя функция `mod`.

**В проекте:** `slideOffset` в `sliders/infinite/engine.js`, `wrapCell` в `gallery/grid.js`.

## 2.9. «Секция на экране?»: IntersectionObserver

Тяжёлые эффекты не должны работать, когда их не видно. Браузер умеет сам сообщать, вошёл
элемент в экран или вышел, — это `IntersectionObserver`. В проекте обёртка:

```js
onViewport(element, {
  enter: () => loop.start(),  // показался — запускаем
  leave: () => loop.stop(),   // ушёл — останавливаем
  rootMargin: '200px',        // считать «видимым» уже за 200 px до экрана
})
```

(`src/core/lifecycle.js`). Плюс ракета проверяет, не закрыт ли весь экран непрозрачными
секциями (`coversViewport` в `rocket/flight.js`): если закрыт — не рисует вообще.

## 2.10. WebGL и three.js

**WebGL** — способ рисовать на видеокарте прямо из браузера. Видеокарта рисует
**треугольники** и раскрашивает их **пиксели**, очень быстро и параллельно. Писать на чистом
WebGL долго, поэтому используют **three.js** — библиотеку, где есть привычные понятия:

| Понятие | Что это | Пример из проекта |
| --- | --- | --- |
| `WebGLRenderer` | «Художник», который рисует в `<canvas>` | один на каждую сцену |
| `Scene` | «Сцена», куда кладут объекты | ракета, площадка, звёзды |
| `Camera` | Откуда смотрим | `PerspectiveCamera` у ракеты, `OrthographicCamera` у плоских эффектов |
| `Mesh` | Объект = **геометрия** (форма) + **материал** (как выглядит) | корпус ракеты |
| `Geometry` | Набор вершин (точек) и треугольников | `LatheGeometry` — тело вращения |
| `Material` | Как красить поверхность | `MeshStandardMaterial` (с освещением), `ShaderMaterial` (свой шейдер) |
| `Texture` | Картинка на поверхности | фото в слайдерах |
| `Points` | Облако точек | звёзды, искры выхлопа |

Минимальная сцена:

```js
const renderer = new WebGLRenderer({ canvas })
const scene = new Scene()
const camera = new PerspectiveCamera(35, width / height, 0.1, 100)
camera.position.z = 10
scene.add(new Mesh(new BoxGeometry(1, 1, 1), new MeshStandardMaterial({ color: 'orange' })))
scene.add(new DirectionalLight('white', 2))
renderer.render(scene, camera) // нарисовать ОДИН кадр; для анимации — в каждом тике
```

### Шейдеры

**Шейдер** — маленькая программа на языке **GLSL**, которая выполняется на видеокарте.
Их два вида:

- **Вершинный (vertex)** — запускается для каждой вершины, решает, **где** она будет на
  экране. Так факел ракеты «колышется», а слайды гнутся на барабан.
- **Фрагментный (fragment)** — запускается для **каждого пикселя**, решает, **какого он
  цвета**. Так делаются переходы между картинками, вода, RGB-сдвиг.

Как передать данные в шейдер:

- **`uniform`** — одно значение на весь кадр, задаётся из JavaScript: время, прогресс
  перехода, позиция мыши. `material.uniforms.uProgress.value = 0.5`.
- **`attribute`** — значение для каждой вершины (позиция, случайное число для звезды).
- **`varying`** — передача из вершинного шейдера во фрагментный (например, координаты
  текстуры `vUv`).

Координаты текстуры (`uv`) идут от (0, 0) в левом нижнем углу до (1, 1) в правом верхнем.
`texture2D(uTexture, uv)` — «взять цвет картинки в этой точке». Почти все эффекты с
картинками — это «взять цвет не из той точки, где пиксель, а чуть сдвинутой».

**В проекте:** все шейдеры лежат в файлах `*.glsl.js` как обычные строки — это работает в
любом сборщике и даже без него.

### Текстуры и CORS

WebGL может взять в текстуру картинку **только со своего домена** (или с чужого, если тот
явно разрешает заголовком CORS). Иначе браузер выдаст ошибку безопасности. Поэтому фото
лежат в `public/photos`, а не грузятся с сайта NASA. Видео в `<video>` показываются без
этого ограничения — их можно грузить с чужого сервера.

### Освобождение ресурсов

У браузера ограниченное число WebGL-контекстов (в Chrome около 16). Когда сцена больше не
нужна, вызывайте `renderer.dispose()` и `renderer.forceContextLoss()`, а у геометрий,
материалов и текстур — `.dispose()`. В проекте это `releaseRenderer` в `core/webgl.js` и
методы `dispose()` в каждой сцене.

## 2.11. Пинг-понг: симуляция на видеокарте

Водная гладь считает волны на видеокарте. Состояние воды (высота и скорость каждой точки)
хранится **в текстуре**. Шейдер читает старое состояние и пишет новое. Но читать и писать
одну и ту же текстуру нельзя — поэтому их **две**, и они меняются ролями каждый шаг: читаем
из A, пишем в B, потом читаем из B, пишем в A. Это и есть «пинг-понг». См.
`modules/liquid/ripple.scene.js`.

## 2.12. Контракт модуля и утечки

Каждый эффект в проекте — **модуль** с одной функцией:

```js
export function init(element, ctx) {
  // ...навесить обработчики, создать анимации...
  return {
    destroy() { /* ...снять ВСЁ, что навесили... */ },
  }
}
```

Если не убирать за собой, получаются **утечки**: обработчики продолжают срабатывать, тикер
крутит анимацию несуществующего элемента, WebGL-контексты заканчиваются. В одностраничном
сайте это незаметно, но в React/Vue/Next, где компоненты постоянно появляются и исчезают,
— главная причина «всё начало тормозить через 5 минут».

Чтобы не забыть ничего, используется **сборщик уборки** `createDisposer()`
(`core/lifecycle.js`):

```js
const d = createDisposer()
d.listen(window, 'resize', onResize)    // повесить обработчик и запомнить, как его снять
d.add(() => gsap.ticker.remove(tick))   // запомнить любую функцию уборки
// ...
d.dispose()                             // выполнить всё в обратном порядке
```

## 2.13. Шина событий

Иногда модулям нужно общаться: когда история доходит до сцены «Разделение», ракета должна
отстрелить ускорители. Но модуль истории не должен знать о ракете (иначе их нельзя
переиспользовать по отдельности). Решение — **шина событий** (`core/bus.js`):

```js
// story/index.js
ctx.bus.emit('story:scene', 2)
// rocket/index.js
ctx.bus.on('story:scene', (index) => { if (index >= 2) separateBoosters() }, { replay: true })
```

`replay: true` — если событие уже было до подписки, подписчик сразу получит последнее
значение. Это нужно, потому что ракета загружается позже истории (ей нужно скачать three.js),
а при перезагрузке браузер может вернуть страницу сразу в середину.

## 2.14. Уважение к пользователю: reduced motion и тач

- **`prefers-reduced-motion: reduce`** — системная настройка «уменьшить движение» (у людей с
  вестибулярными нарушениями от анимаций может кружиться голова). В проекте при ней:
  нет плавного скролла, интро, дрейфа, инерции, автозапуска видео; всё, что двигается само,
  выключено, а то, что двигает сам пользователь, работает мгновенно.
- **Тач-экраны** (`pointer: coarse`) — нет курсора, значит, не нужен ни кастомный курсор, ни
  эффекты наведения. Видеопанели раскрываются тапом.

Проверить reduced motion: DevTools → ⋮ → More tools → Rendering → «Emulate CSS media feature
prefers-reduced-motion».
